# ADR-0001. Способ доставки кода на сервер

**Статус:** принято
**Дата:** 2026-10-05

## Контекст

TimeCapsule развёрнут на одном экземпляре EC2 (nginx + PHP-FPM + PostgreSQL). Код меняется, и нужен надёжный способ выкладывать новые версии. Требования: понимать, какая версия сейчас работает на сервере; не терять изменения; уметь быстро откатиться; чтобы код хранился в общем месте, а не на ноутбуке разработчика. Ограничения: нет CI/CD-системы, репозиторий публичный, секреты не должны попадать в репозиторий, сервер один, а выкладки редкие.

## Решение

Единственный источник кода - репозиторий GitHub. Сервер сам забирает код из публичного репозитория по HTTPS, а выкладку выполняет человек вручную по SSH. Последовательность команд на сервере:

```
cd /var/www/timecapsule
git pull
composer install --no-dev --optimize-autoloader
php bin/init-db.php
sudo systemctl reload php-fpm
```

Откат выполняется через репозиторий: на компьютере `git revert --no-edit HEAD` и `git push`, затем та же последовательность команд на сервере. Править код прямо на сервере запрещено.

## Рассмотренные альтернативы

1. **Копирование через `scp`.** Просто для нескольких файлов, ничего не нужно настраивать на сервере. Отвергнуто: непонятно, какая версия работает на сервере; легко забыть файл; нет истории и надёжного отката; код живёт на компьютере разработчика; библиотеки и таблицы БД приходится обновлять отдельно.
2. **Скрипт `deploy.sh`.** Те же шаги выполняются одной командой, в нужном порядке; `set -euo pipefail` останавливает выкладку при первой ошибке; скрипт можно запускать удалённо по `ssh`. Отвергнуто на данном этапе: для одного сервера и редких выкладок выигрыш небольшой, а сам скрипт нужно поддерживать и хранить. Он остаётся естественным следующим шагом, когда команд станет больше или выкладки участятся.
3. **`git pull` вручную на сервере (выбрано).** Версия сервера определяется коммитом, есть история изменений и откат через `git revert`. Выкладка прозрачна: каждая команда выполняется и проверяется глазами, что полезно для понимания процесса и отладки.

## Последствия

**Плюсы:** простота, не нужно ничего дополнительно настраивать и поддерживать; полный контроль над каждым шагом; на сервере всегда известен коммит; безопасный откат через репозиторий; сервер имеет доступ только на чтение, поэтому его взлом не позволяет изменить код в репозитории; секреты остаются в `.env` вне git.

**Минусы и риски:** человеческий фактор: можно забыть шаг (`composer install`, `php bin/init-db.php`, перезагрузку PHP-FPM) или выполнить их в неверном порядке, и сайт сломается; нет остановки при ошибке, как в `set -e`, поэтому следующая команда может выполниться после неудачной предыдущей; процесс не воспроизводим и плохо масштабируется на несколько серверов; нет тестов и проверки после выкладки, поэтому сломанный коммит может попасть на сервер (показано в задании 13); во время `git pull` файлы заменяются по одному, и посетитель может на секунды увидеть неконсистентное состояние.

**Дальнейшее улучшение:** оформить шаги в `deploy.sh`, добавить CI (проверка `php -l` и тестов), автоматический запуск деплоя по `git push`, smoke test после выкладки и выкладку в новый каталог с переключением символической ссылки.
