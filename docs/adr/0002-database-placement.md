# ADR-0002: Размещение базы данных в приватной подсети

- **Статус:** Принято (для архитектуры лабораторной работы №3)
- **Дата:** 2026-10-21
- **Проект:** TimeCapsule
- **Окружение:** dev
- **Регион AWS:** eu-central-1 (Frankfurt)
- **Связанные материалы:** ЛР2, ЛР3 «Cloud Networking», задание 14

## Контекст

В лабораторной работе №2 приложение TimeCapsule и PostgreSQL размещались на одном EC2-сервере в default VPC. Для лабораторной работы №3 необходимо перенести приложение в собственную VPC `timecapsule-dev-vpc` (`10.7.0.0/16`) и отделить базу данных от веб-приложения. При этом пользователи должны иметь доступ к приложению по HTTP, а PostgreSQL не должен быть доступен напрямую из интернета.

Сеть содержит четыре подсети в двух зонах доступности:

| Подсеть | Зона | CIDR | Назначение |
|---|---|---|---|
| `timecapsule-dev-public-a` | eu-central-1a | `10.7.0.0/24` | `app-server`, временный NAT Gateway |
| `timecapsule-dev-public-b` | eu-central-1b | `10.7.1.0/24` | `bastion` |
| `timecapsule-dev-private-a` | eu-central-1a | `10.7.10.0/24` | `db-server` |
| `timecapsule-dev-private-b` | eu-central-1b | `10.7.11.0/24` | резерв для будущих ресурсов |

## Рассмотренные варианты

### Вариант 1. PostgreSQL на одном сервере с приложением

**Преимущества:** минимальное число EC2-экземпляров; простое подключение к БД через `localhost`; нет отдельной настройки сетевого доступа.

**Недостатки:** приложение и база разделяют ресурсы одного сервера; отказ сервера останавливает оба компонента; сложнее изолировать БД и независимо обслуживать её.

### Вариант 2. PostgreSQL на отдельном сервере в публичной подсети

**Преимущества:** независимые вычислительные ресурсы для приложения и БД; отдельное обслуживание; простой доступ к репозиториям пакетов при наличии публичного IP и маршрута через Internet Gateway.

**Недостатки:** при назначении публичного IP и ошибках в правилах фильтрации БД может стать доступной из интернета; публичное размещение увеличивает риск неверной конфигурации; публичный IP не нужен для нормальной работы PostgreSQL.

### Вариант 3. PostgreSQL на отдельном сервере в приватной подсети

**Преимущества:** нет публичного IP и постоянного маршрута в интернет; доступ к порту 5432 ограничен Security Group приложения; SSH возможен через bastion; сервер базы обслуживается независимо от приложения.

**Недостатки:** требуется дополнительный EC2-экземпляр и диск; настройка сети сложнее; для загрузки обновлений нужен временный выход в интернет или иной управляемый способ доставки пакетов.

## Решение

**Выбран вариант 3:** PostgreSQL размещается на отдельном экземпляре `timecapsule-dev-db` в `timecapsule-dev-private-a` (`10.7.10.0/24`) **без публичного IPv4-адреса**.

- Приложение размещается на `timecapsule-dev-app` в `timecapsule-dev-public-a` и получает постоянный Elastic IP для пользовательского HTTP-доступа.
- Административный SSH-доступ с моего текущего внешнего IP разрешён только к `timecapsule-dev-bastion` в `timecapsule-dev-public-b`. Подключение к `app-server` и `db-server` выполняется через SSH ProxyJump.
- `timecapsule-dev-web-sg`: входящий TCP/80 из `0.0.0.0/0`, TCP/22 от `timecapsule-dev-bastion-sg`.
- `timecapsule-dev-db-sg`: входящий TCP/5432 от `timecapsule-dev-web-sg`, TCP/22 от `timecapsule-dev-bastion-sg`.
- PostgreSQL слушает сетевые интерфейсы, а `pg_hba.conf` допускает пользователя `timecapsule` к базе `timecapsule` только из `10.7.0.0/24` с проверкой `scram-sha-256`.
- Приватная зона Route 53 `timecapsule.internal` содержит запись `db.timecapsule.internal` на приватный IP `db-server`. Приложение использует это имя как `DB_HOST`.
- `timecapsule-dev-public-rt` содержит локальный маршрут `10.7.0.0/16` и маршрут `0.0.0.0/0` через `timecapsule-dev-igw`. `timecapsule-dev-private-rt` в обычном режиме содержит только локальный маршрут.

## Последствия

### Обновления и стоимость

У `db-server` нет постоянного выхода в интернет. Для установки PostgreSQL и обновлений безопасности временно создаётся **публичный NAT Gateway** `timecapsule-dev-nat-a` в `public-a` с Elastic IP. В `private-rt` на время обновления добавляется маршрут `0.0.0.0/0` к NAT Gateway. После установки пакетов маршрут удаляется, NAT Gateway удаляется, а выделенный ему Elastic IP освобождается.

NAT Gateway оплачивается за время существования и объём обработанного трафика; Elastic IP также может тарифицироваться. Поэтому временное использование снижает расходы по сравнению с постоянно работающим NAT Gateway. В ЛР3 приведена оценка затрат на NAT за короткую установку — **центы**, без фиксированной гарантированной суммы; фактическая стоимость зависит от длительности и трафика. За EC2 и EBS начисляются отдельные платежи согласно использованию.

Для специальности **Informatică** временный NAT создаётся и удаляется скриптами `scripts/nat-up.sh` и `scripts/nat-down.sh`; для **Informatică aplicată** допускается работа через консоль AWS.

### Зачем приложению Elastic IP

`app-server` должен иметь стабильный адрес для пользователей и параметра `APP_URL`. Обычный автоматически выданный публичный IPv4 может измениться после остановки и запуска EC2. Elastic IP сохраняет адрес, пока он выделен и привязан в нужной конфигурации. Он оплачивается в том числе во время остановки экземпляра, пока адрес выделен.

Если позднее перед приложением появится публичный балансировщик нагрузки, пользователи смогут обращаться к DNS-имени балансировщика, а `app-server` можно будет разместить за ним без собственного публичного Elastic IP. Для постоянного статического IP у самого балансировщика потребуются дополнительные решения в зависимости от типа балансировщика.

### Надёжность и ограничения

- База изолирована от прямых входящих подключений из интернета, но остаётся доступной приложению внутри VPC.
- Для доступа к базе необходимы одновременно разрешённый сетевой путь, правила Security Group, разрешение в `pg_hba.conf` и корректные учётные данные PostgreSQL.
- Размещение одного `db-server` в `eu-central-1a` **не обеспечивает отказоустойчивость по зонам доступности**. Для этого в дальнейшем понадобятся резервирование/репликация БД, резервный экземпляр в другой AZ и механизмы переключения.
- Загруженные пользователями файлы, оставшиеся на диске `app-server`, не защищены переносом одной только базы; для устойчивости потребуется отдельное хранилище или резервное копирование.
- Если `db-server` пересоздан с другим приватным IP, необходимо обновить A-запись `db.timecapsule.internal`.

## Проверка решения

Доказательства реализации прикладываются к отчёту `docs/lab3/README.md`:

1. `db-server` находится в `private-a` без публичного IP; `private-rt` не имеет постоянного маршрута в интернет.
2. С `app-server` выполняется подключение `psql` к `db.timecapsule.internal:5432`.
3. С `bastion` TCP/5432 недоступен, несмотря на существование локального маршрута VPC.
4. После удаления NAT Gateway `db-server` не может обратиться к внешнему сайту, но PostgreSQL продолжает обслуживать запросы приложения.
5. После переноса данных `/health` сообщает о доступности БД, а ранее созданные капсулы видны в приложении.

> Этот ADR фиксирует принятое архитектурное решение. Результаты проверок следует подтвердить реальными командами и скриншотами, а не считать автоматически выполненными.
