# ADR-0003: Хранение вложений TimeCapsule в Amazon S3

- **Статус:** принято
- **Дата:** 2026-11-09
- **Проект:** TimeCapsule
- **Автор:** Каралащук Илья, IA2403
- **Контекст:** Cloud Computing, лабораторная работа №4 (продвинутый уровень)

## Контекст

До миграции вложения капсул хранились в `storage/uploads` на локальном диске EC2 `app-server`. При пересоздании инстанса, масштабировании на несколько серверов или переключении трафика файлы были бы недоступны на другом экземпляре приложения. Требуется вынести пользовательские файлы из жизненного цикла EC2, ограничить доступ и сохранить возможность отображения изображений и скачивания документов.

## Рассмотренные варианты

| Критерий                   | Amazon EBS на EC2                           | Amazon EFS                           | Amazon S3                                    |
|----------------------------|---------------------------------------------|--------------------------------------|----------------------------------------------|
| Доступ                     | Блочное устройство, привязка к EC2/AZ       | Общая POSIX-файловая система по сети | Объектный API HTTPS                          |
| Несколько серверов         | Требует особой схемы подключения/репликации | Общий доступ нескольких EC2          | Все экземпляры используют один бакет         |
| Сохранность при замене EC2 | Нужно управлять томом и его подключением    | Данные не привязаны к одному EC2     | Данные не привязаны к EC2                    |
| Версионирование            | Снимки EBS, управление отдельно             | Бэкапы и управление отдельно         | S3 Versioning и delete markers               |
| Стоимость                  | Ёмкость и тип тома                          | Ёмкость и операции/режимы EFS        | Хранение, запросы, передачи, классы хранения |
| Изменения кода             | Минимальные                                 | Минимальные                          | Нужен AWS SDK и работа с ключами объектов    |

## Решение

**Выбрано Amazon S3**: бакет `timecapsule-dev-uploads-iliuha2006` в `eu-central-1`, ключи `uploads/<случайное имя>`. Для PHP Functional модуль `src/storage.php` использует AWS SDK for PHP: `PutObject` для сохранения, `DeleteObject` для удаления и `GetObject` с подписанным URL для скачивания. Сервер EC2 получает временные учётные данные через IAM-роль `timecapsule-dev-app-role`, а не из `.env`.

Бакет не является публичным: включён Block Public Access, используется SSE-S3, а Bucket Policy запрещает HTTP. Политика приложения ограничена действиями `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` на `uploads/*`. После завершения миграции удалено разрешение `s3:ListBucket`, которое было нужно для `aws s3 sync`.

## Последствия

### Доступ пользователя к вложению

Приложение проверяет права пользователя на капсулу, затем создаёт подписанный URL `GetObject` на **5 минут** и отвечает HTTP `302 Redirect`. Браузер получает содержимое непосредственно от S3; срок ограничен параметром `X-Amz-Expires` и действительностью подписывающих временных учётных данных. URL является bearer-ссылкой: до истечения срока его может использовать любой, кто получил адрес. Исходное имя файла и тип содержимого передаются в заголовках ответа S3.

### Защита и стоимость

Versioning сохраняет предыдущие версии объектов, а обычное удаление создаёт delete marker. Приложению не разрешено `s3:DeleteObjectVersion`, что снижает риск необратимого удаления версий через его учётные данные. Правило `timecapsule-dev-noncurrent` переводит неактуальные версии в Standard-IA через 30 дней и удаляет их через 90 дней с сохранением двух более новых неактуальных версий; незавершённые multipart-загрузки отменяются через 7 дней. Стоимость S3 всё равно зависит от объёма, запросов и исходящего трафика; хранение старых версий не бесплатно.

### Масштабирование и отказоустойчивость

Несколько экземпляров `app-server` за балансировщиком нагрузки смогут обращаться к одним и тем же объектам S3, используя одинаковую политику IAM и настройки бакета. Для замены инстанса не требуется переносить локальные вложения: достаточно развернуть приложение, настроить подключение к базе и прикрепить роль EC2. Amazon S3 в регионе хранит данные с устойчивостью к отказам отдельных зон доступности, но **это не защита от потери целого региона**; для региональной катастрофоустойчивости понадобится отдельное решение (например, Cross-Region Replication и план восстановления).

### Ограничения и риски

- Код зависит от AWS SDK, S3 API и сетевой доступности сервиса.
- Ошибки IAM и неверные ARN приводят к `AccessDenied` даже при корректном коде.
- Presigned URL нельзя менять после подписи; при пересылке до истечения срока он остаётся доступен получателю.
- Локальные операции с файлами и предположения о POSIX-пути должны быть удалены из приложения.
- Приложение остаётся зависимым от базы данных; вынос вложений сам по себе не делает всё приложение полностью stateless.

## Итог

S3 выбран как наиболее подходящее хранилище вложений TimeCapsule: оно отделяет файлы от EC2, обеспечивает удобное разграничение прав, версионирование, lifecycle-управление и прямую безопасную выдачу файлов через временные ссылки. Издержки на доработку модуля хранения оправданы упрощением масштабирования и восстановления сервера.
