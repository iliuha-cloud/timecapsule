# ADR-0004: Размещение базы данных приложения TimeCapsule

- **Статус:** принято
- **Дата:** 2026-11-24
- **Автор:** Каралащук Илья
- **Связанные документы:** ЛР3 (PostgreSQL на `db-server`), ЛР4 (схема инфраструктуры), ЛР5 (перенос в RDS)

## Контекст

База приложения TimeCapsule (таблицы `users`, `capsules`) работала на отдельном сервере `db-server` (EC2, PostgreSQL без публичного IP, подсеть `private-a`). Обновления СУБД и ОС приходилось ставить вручную через временный NAT Gateway, автоматических резервных копий не было, поэтому любая ошибка в данных или потеря диска означала потерю данных.

Требования к решению:

- база недоступна из интернета, подключаться могут только серверы приложения;
- восстановление данных после ошибки (случайный `DELETE`, битая миграция);
- минимум ручного администрирования;
- расходы до конца курса (≈ 3 месяца) в пределах нескольких десятков долларов;
- приложение не должно менять конфигурацию: `DB_HOST=db.timecapsule.internal`.

## Рассмотренные варианты

| Критерий | PostgreSQL на EC2 | RDS, одна зона | RDS Multi-AZ | Amazon Aurora |
|---|---|---|---|---|
| Обновления СУБД и ОС | вручную | AWS, в окно обслуживания | AWS, в окно обслуживания | AWS, в окно обслуживания |
| Резервные копии | нужно настраивать самому (`pg_dump`, снимки EBS) | автоматические, восстановление на любой момент за 1–35 дней | то же | автоматические, непрерывные |
| Отказ зоны доступности | база недоступна, восстановление вручную | база недоступна, восстановление из копии в другой зоне | автоматический переход на резервный экземпляр в другой зоне (порядка 1–2 минут) | реплики в других зонах, быстрый переход |
| Стоимость (оценка для нашей нагрузки) | EC2 + EBS, плюс время на администрирование | ≈ $13–14 за 3 месяца при работе ≈ 3 ч в день | примерно вдвое дороже: экземпляр и хранилище удваиваются (≈ $26) | дороже: минимальный класс экземпляра крупнее `t4g.micro`, I/O и хранилище оплачиваются отдельно |
| Остановка для экономии | можно остановить EC2 | можно остановить на срок до 7 дней | можно остановить на срок до 7 дней, но шаблон Sandbox этот вариант не предлагает | кластер можно остановить до 7 дней |
| Сложность | высокая (всё на нас) | низкая | низкая | средняя |

Цены ориентировочные и взяты из оценки в методичке ЛР5 (eu-central-1, октябрь 2026); перед реальным использованием их нужно проверять в AWS Pricing Calculator.

## Решение

Размещаем базу приложения в **Amazon RDS for PostgreSQL в одной зоне** (`timecapsule-dev-rds`, `db.t4g.micro`, 20 ГиБ gp3, зона `eu-central-1a`, без публичного доступа, с шифрованием), а не на EC2.

Причины:

1. RDS закрывает главные проблемы `db-server`: обновления и резервные копии берёт на себя AWS.
2. Multi-AZ и Aurora защищают от отказа зоны, но для учебного окружения без реальных пользователей это двойная или большая цена без пользы.
3. Одна зона вместе с резервными копиями даёт приемлемый риск: данные можно восстановить, пусть и с простоем.
4. Группа подсетей `timecapsule-dev-db-subnets` включает `private-a` и `private-b`, поэтому при необходимости базу можно восстановить или перенести в другую зону без перестройки сети.

Для рабочей системы с реальными пользователями решение нужно пересмотреть в пользу Multi-AZ (или Aurora).

## Последствия

### Резервные копии и потеря данных

- Автоматические резервные копии включены, срок хранения 7 дней: ежедневный снимок плюс журнал изменений, который RDS сохраняет примерно раз в 5 минут.
- Базу можно восстановить на любой момент в пределах 7 дней (Point-in-time restore) до значения *Latest restore time*. Восстановление создаёт **новую** базу, старая не изменяется.
- В худшем случае теряются последние ≈ 5 минут данных (RPO ≈ 5 минут).
- Реплика для чтения **не** заменяет резервную копию: она повторяет и ошибочный `DELETE` (проверено в ЛР5, часть 1).

### Стоимость и расходы

- Оценка: ≈ $13–14 за 3 месяца при работе ≈ 3 часа в день (экземпляр ≈ $5, хранилище 20 ГиБ gp3 ≈ $8; резервные копии в пределах объёма хранилища бесплатны; EventBridge Scheduler бесплатен).
- Расходы ограничены тремя мерами: самый маленький класс `db.t4g.micro`, фиксированное хранилище 20 ГиБ без автоматического увеличения, ночная остановка базы расписанием `timecapsule-dev-rds-nightly-stop` (`cron(0 23 * * ? *)`, часовой пояс Europe/Chisinau). Роль расписания может останавливать только эту базу.
- Остановленную базу AWS запускает сам через 7 дней, после чего она работает и оплачивается круглосуточно. Следующий запуск расписания остановит её в 23:00 того же дня, то есть перерасход ограничен менее чем одним днём работы (≈ $0,46 за сутки). Хранилище оплачивается всегда, даже у остановленной базы (≈ $2,6 в месяц).
- Если не запускать базу вручную в начале занятия, приложение не работает (`/health` показывает ошибку базы): это сознательный компромисс.

### Как приложение находит базу и отказ зоны eu-central-1a

- Приложение обращается к `db.timecapsule.internal` (`DB_HOST` не менялся). В приватной зоне Route 53 это запись CNAME на endpoint `timecapsule-dev-rds`. Endpoint при остановке и запуске базы не меняется, поэтому конфигурацию приложения менять не нужно.
- RDS принимает только зашифрованные соединения: PHP и `psql` включают шифрование сами, для Node.js в `.env` задан `PGSSLMODE=no-verify` (канал шифруется, сертификат сервера не проверяется).
- База находится в `eu-central-1a` и без Multi-AZ при отказе этой зоны **недоступна**; `app-server` тоже находится в `eu-central-1a`, поэтому недоступно всё приложение. План восстановления: восстановить базу из резервной копии в `eu-central-1b` (подсеть `private-b` входит в группу подсетей), изменить CNAME `db` на новый endpoint, запустить приложение в `public-b`. Ожидаемый простой: десятки минут, потеря данных до ≈ 5 минут.
- Чтобы пережить отказ зоны автоматически, нужны RDS Multi-AZ и второй сервер приложения в другой зоне; это примерно удвоит расходы на базу.

### Прочие последствия

- Пользователь `dbadmin` используется только для администрирования, приложение работает под отдельным пользователем `timecapsule` (владелец своей базы).
- Нужно помнить: запускать базу в начале занятия первой, останавливать после занятия.
- Сервер `db-server` больше не нужен и удалён; обновления СУБД и ОС выполняет AWS, поэтому временный NAT Gateway для обновления базы не требуется.
